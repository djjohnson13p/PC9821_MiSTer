**Verdict: PASS. Yes, push `fix-pg-accept-resp` as it stands.** Both commits are correct and
cycle-neutral on every model that answers a cycle or more after the accept. The fail-first holds

## 1. The defect, reproduced and pinned to its mechanism

`5394cc5`'s RTL is `0ebf0d0`'s. On that tree, the same pc98-map programs that the commit names time
out under `+zero_wait`, and only under `+zero_wait`. Each was run in both response widths:

| program | `+zero_wait` | `+zero_wait +no_line_fill` | default model |
|---|---|---|---|
| `lock_window` | TIMEOUT | TIMEOUT | PASS |
| `rmw_device_reads` | TIMEOUT | TIMEOUT | PASS |
| `pc98_direct_read_shapes` | TIMEOUT | TIMEOUT | PASS |
| the other five pc98-map programs | PASS | PASS | PASS |

I confirmed the stated mechanism with a sim-only probe on `5394cc5` (not committed). On the first
DIRECT read, `linear=000a8000`, it fires `PG_MEM_TLB` `req_mem_dcache_accept && dcache_req_complete`
with `fast_path_pending` (old) = 0. Five thousand cycles later the probe reports
`fast_path_pending=1 mem_servicing=1 mem_opt_wait=1`, with the state machine in `PG_IDLE` and no
request presented. That is the wedge the commit describes: the clear tested a flag that was still
0, and the set came after it. It also shows `mem_opt_wait` stuck through the grace pulse.

On `5227777`, all eight programs pass in both widths. So do `make test-pc98-map` and
`make test-protected-zero-wait` (309/309 twice).

## 2. Correctness

### 2.1 Which paths can complete on their own accept edge

The mechanism sets the scope. In `bus_unit.sv`, a demand read completes in the accept cycle only
through `direct_rd_resp_now`:

```
resp_valid && (direct_rd_pending || (ext_direct_accept && !ext_write_r))
```

`ext_direct_accept` is `ext_valid_r && ready && DIRECT`, and `ext_valid_r` is registered from the
launch. An L1 read cannot complete in its accept cycle, because `l1_cache.sv` `cpu_resp_valid` is
`lookup_read_hit_now || resp_valid_r`, both registered past the accept. That leaves two ways a read
can reach a same-edge completion:

1. A DIRECT read that the requester still presents in the cycle after its launch.
2. Any request that the paging unit registers into `dcache_req_valid_r` before the accept.

Each `paging_unit` accept path checks out as follows:

| path | presented by | can complete on its accept edge? | state of the flag at that edge | verdict |
|---|---|---|---|---|
| `PG_MEM_TLB` single read | `req_mem_dcache_candidate` (live, held until accepted) | **yes** (DIRECT, cycle 2+) | set at the same edge -> **the defect** | fixed: `req_mem_acc_done` -> no flag, no grace, `PG_IDLE` |
| `PG_MEM_TLB` crossing first half, read | same | **yes** | `PG_CROSS_WAIT1` waited for a completion already past -> wedge | fixed: -> `PG_CROSS_PREP2` |
| `PG_MEM_TLB` write / crossing write | same | yes | already handled by `req_mem_posted_done` | unchanged in effect |
| `PG_IDLE` `pretrans_accept` | `pretrans_present` (one cycle only, `PG_IDLE`) | **no**. A DIRECT pretrans read launches in that cycle and can be accepted only a cycle later, by which time the state is `PG_MEM_TLB` and the request is re-presented by the candidate path. An L1 pretrans read answers a cycle later at the earliest. | n/a | safe as left |
| `PG_IDLE` `early_wr_accept` | write | yes (posted) | it never sets the flag, and it clears `mem_servicing` itself | safe |
| `PG_IDLE` I/O / INTA | `dcache_req_valid_r` (registered) | yes, from the next cycle on | `fast_path_pending` already 1 at the edge it was registered | safe |
| `PG_IDLE` I/O crossing | registered -> `PG_CROSS_WAIT1` | yes | the state is already `WAIT1` | safe |
| walker `emit_single` / `emit_first_half` | registered | yes | the flag or `WAIT1` is set with the registration | safe |
| crossing second half (`emit_second_half`) | registered -> `PG_CROSS_WAIT2` | yes | the state is already `WAIT2` | safe |
| x87 sink | I/O only (`dcache_req_is_x87_r`) | yes | registered I/O path | safe |

**I checked the `pretrans_accept` path empirically as well.** A second sim-only probe on `5227777`
`$fatal`s on `s_idle && idle_mem_req && pretrans_accept && dcache_req_complete`. The whole suite ran
under it in three configurations: `+zero_wait`, `+zero_wait +no_line_fill` and `+mem_latency=0`. So
did the eight pc98-map programs. Everything passed (309/309 and 8/8 each). The pretrans path was
taken in 211, 212 and 213 programs respectively, and in 4 of the pc98 programs. It never completed
on its accept edge. The same probe confirms that both new arms are exercised under `+zero_wait`: the
non-crossing read in 3 pc98 programs and the crossing first half in 1.

**I also forced the `pretrans_accept` path directly, at the coordinator's request.** The
re-vendor lane pointed out that this arm has the same set-after-clear shape: it does
`fast_path_pending <= 1` after the `dcache_req_complete` clear. I wrote a scratch program,
`rv3_pretrans_direct` (pc98 map, paging on, not committed). It runs 200 iterations of DIRECT
(`0xA8000`) and `0xE0000` loads through the VIPT slow-submit (pretranslated) path. The loads are
interleaved with DIRECT writes, an I/O read, cached RAM loads and back-to-back dependent DIRECT
loads, and the probe `$fatal` above was armed. It passed, and the probe never fired, in every
configuration:

| configuration | pretrans presented in `PG_IDLE` | of those, deferred to `PG_MEM_TLB` |
|---|---|---|
| `+zero_wait` | >= 300 | all of them |
| `+zero_wait +no_line_fill` | >= 300 | all of them |
| `+zero_wait +z486_cache_off` | >= 500 | >= 300, and the rest accepted by the L1 in `PG_IDLE` |
| `+mem_latency=0` and `3` | the same as `+zero_wait` | all of them |

That is the structure in the table above. A DIRECT pretrans read is never accepted in `PG_IDLE`,
because its bus cycle is only launched there. It is accepted in `PG_MEM_TLB`, which is the arm this
fix covers. A pretrans read that the L1 accepts in `PG_IDLE` completes no earlier than the next
cycle.

**The shape is therefore not reachable with this `bus_unit`/`l1_cache`, and this review does not
change it.** It would become reachable if either of two things changed:

- the L1 gained a combinational accept-to-response path (a hit answered in the cycle `cpu_valid`
  rises);
- `bus_unit` let a DIRECT request be accepted in its launch cycle.

**Recommended hardening, not required for this push (H1).** Add a SIM-only guard beside the
existing `pretrans_valid` check in `paging_unit.sv`:
`if (reset_n && s_idle && idle_mem_req && pretrans_accept && dcache_req_complete) $fatal(1, ...)`.
Mirroring the `PG_MEM_TLB` treatment in this arm (clear `mem_servicing` and skip the flag on
`dcache_req_complete`) would NOT be enough. The arm latches its OPR_R metadata on the accept edge
itself, so a completion on that edge would still extract with the previous request's lanes. That
is the failure the ablation in section 2.2 produced. The assertion is therefore the right guard: a
future change to the cache timing would fail loudly instead of wedging or returning wrong data.

**Page-crossing reads.** `pc98_direct_read_shapes` crosses only dword boundaries. To cover page
crossings, I added a scratch program (`rv3_direct_pagecross`, not committed). It runs four DIRECT
reads: a dword and a word across `0xA8FFF/0xA9000`, with `INVLPG` of the second page first so that
`PG_CROSS_TLB2` walks; a dword across `0x9FFFE` (RAM -> window); and a 3+1-byte read. The results:

| tree | `+zero_wait` | `+zero_wait +no_line_fill` | default model |
|---|---|---|---|
| `5394cc5` | TIMEOUT | TIMEOUT | PASS |
| `5227777` | PASS | PASS | PASS |

The default-model cycle counts are identical on the two trees (416 at latency 0, 570 at latency 7).
The second half and the walk after an accept-cycle first half follow the old `WAIT1 -> PREP2` path
unchanged, one cycle earlier.

**Faults and aborts in the accept cycle.** There are none. `req_mem_dcache_candidate` requires
`!req_perm_fault` and `req_can_translate`, so a request that is accepted cannot fault in that
cycle. A TLB miss walks before any request is presented. A page fault on the second half of a
crossing happens in `CROSS_TLB2/WALK2`, after `PREP2`, exactly as before. `paging_unit` has no
abort or flush input that leaves the state machine mid-request.

**Reset.** Nothing new is added. `fast_path_pending`, `mem_dly_grace`, `mem_opt_wait` and the
`opr_*` registers are all in the async reset branch.

**Grace and `mem_opt_wait`.** An accept-cycle read now raises no `mem_dly_grace`, so `mem_opt_wait`
is never set for it. The posted-write arm already worked this way. The sequencer sees
`mem_servicing` low on the next cycle, with `OPR_R` written on the accept edge itself. Nothing is
left waiting on a pulse.

### 2.2 The OPR_R metadata latch in `PG_IDLE`

**Correct.** The new `latch_biu_meta` in the `PG_IDLE -> PG_MEM_TLB` arm writes the values that
`PG_MEM_TLB` writes on its accept edge:

- `linear_addr[1:0]` is `req_offset`, because `latch_mem_request` captures `addr[1:0]` on the same
  edge.
- `mem_op_size` is `req_op_size`.
- `idle_mem_crossing` is `req_crossing`.
- The crossing variant uses `first_half_bytes(...) - 1`, exactly as `PG_MEM_TLB` does.

**Necessary, and tested.** I ran an ablation: `5227777` with only this latch removed. It fails
`pc98_direct_read_shapes` with **wrong data** (`Failure data: 0`, test failed, no timeout) in both
widths. Without the latch, the accept-edge OPR_R write uses the previous request's lanes. Those can
include `opr_suppress_r` from an INTA, or `opr_is_walk_r` from a walk.

**Cycle-neutral.** No demand read can be outstanding while `PG_IDLE` captures a new request, because
`idle_data_req` requires `!mem_servicing`. So the one-cycle-earlier write of the same values can
only be observed by a completion on the accept edge itself. A posted write that may still be in
flight from `early_wr_accept` does not drive `dcache_read_complete`. The `PG_IDLE` capture already
overwrote `opr_is_write_r`, as the pretrans, early-write and I/O arms did before this change.

**Complete.** `PG_MEM_TLB` is entered from exactly two places:

1. The `PG_IDLE` arm, which now latches.
2. `complete_check_only` with `req_cross_pre`, which is a paged write whose completion never
   produces a read return.

So no read can reach the accept-edge completion without the latch.

The latch also widens the `opr_*` enable to the whole `idle_mem_req && !io` arm. That is no
timing concern: the pretrans and early-write arms already latched from `linear_addr[1:0]` and
`mem_op_size`. The enable loses its `dcache_req_accepted` term, if anything.

### 2.3 The bench model (`5394cc5`)

`zw_fire` and `zw_line_fire` are gated on `valid && ready && cpu_ce && !write && !inta && !rd_busy`
and on no response back-pressure. The data comes from `mem[]` combinationally, I/O uses the same
port decode as the registered path, and the burst bookkeeping (`rd_index`, `rd_remaining`, `ready`)
is consistent for single-beat reads, narrow bursts and whole-line fills. The default model is
untouched when the plusarg is absent: the cycle logs in section 3 are byte-identical to the author's.

## 7. Answer

**Push: YES.** The fix closes the window for every path that can complete on its accept edge
(section 2.1). Its metadata latch is correct, necessary (the ablation fails with wrong data),
cycle-neutral and complete. Both claims of the fail-first hold for the stated reason. Cycles are
byte-identical across 981 program-latency rows, 30 microbenchmark rows, the pc98 set and Dhrystone.
The release gate and 360 extra zero-wait fuzz seeds are green. The upstream claim is verified. The `pretrans_accept` arm has the same textual shape, but forcing it showed it cannot be reached with this cache and bus timing (section 2.1). Guarding it is recommended hardening (H1), not a condition for this push.
