BEGIN:TIME
TIME: the timing ladder. Every figure is a RATIO against two counters a 486 can read: the
  free-running counter at 005C (low word) / 005E (high word), and the PIT's channel 0 read
  through its own counter-latch command. /TIMEREF measures both counters against the
  calendar's second and converts these rows to Hz, nanoseconds and 50 MHz core cycles.
  READ-ONLY as far as live state goes. The only writes /TIME makes are 0077 <- 00 (the PIT
  counter-latch command: it copies the counter into the latch register and changes no state,
  and it is deliberately NOT in the RESTORE table, because 0077's read-back is FF and
  replaying FF would write a PIT MODE word) and 005F (the documented I/O-wait port, a
  write-only delay generator, recorded in RESTORE). Every other access is a read.
  ARTIC 005C/005E = 3BFAFA15
  ARTIC again after the PIT samples below = 3BFBFB77 (delta = 00010162 ticks)
  work-area 0501 bit 7 (the byte the BIOS's own PIT setup tests at BANK7@0x5DE7) = 00
    -> the BIOS's own divisor here is 0x6000 = 24576, so it expects a 2.4576 MHz counter

  PIT channel 0 latch/read, three samples = 208A 207E 2075
    measured divisor = 7E7A (largest count over a 20 ms scan; mode 3 sweeps divisor..0 in steps of 2)
  work-area 054D bit 2 (the GDC clock the BIOS published: 0 = 2.5 MHz, 1 = 5 MHz) = 00
  I/O access time: 1024 back-to-back accesses per class, cli across each class's window, no DOS call inside it.
  BASE is the same loop with the bus access replaced by a same-length register move, so the
  excess columns are ONE access over a non-I/O instruction of the same shape; they include the
  CPU's own cost of the instruction, which a 486 cannot separate from the bus time, so each is
  an upper bound on the device's share. The ns columns use the DOCUMENTED rates (ARTIC
  307200 Hz, PIT 2.4576 MHz); /TIMEREF measures both and reprints these rows corrected.

BEGIN:TIMEREF
TIMEREF: the calendar (uPD4990A) as an absolute reference. Its 32.768 kHz crystal is
  independent of the PIT's oscillator, whose value - 2.4576 MHz or 1.9968 MHz, 23% apart - is an
  unmeasured premise (r12/02 P1-4) that every time base in this core inherits. This section
  writes the calendar's command latch at 0020 exactly as the ITF's own INT 1Ah reader does
  (BANK7@0x5D22: TIMEREAD, SHIFT, then clocks on 0033 bit 0, leaving the latch at 07); it
  writes the calendar's COUNTERS only when /TIMESET is given. cli covers each bit sequence.
  0022 mode latch (first touch) = EF
  0128 = 81 (calendar tick rate, 0x80|rate; this read also clears a pending tick)
  full read: 52 bits from 0033 bit 0, then the six fields decoded both ways - the uPD4993A
  four-bit prefix question (r6/08 C19) is what separates the two lines:
    1010000010000000000000000000000000000000000000001000
    payload at bit 0: sec=05 min=01 hour=00 day=00 mon/wday=00 year=00  (valid BCD)

    payload at bit 4: sec=10 min=00 hour=00 day=00 mon/wday=00 year=10  (valid BCD)
  /TIMESET given: writing the calendar's own counters with the ITF's own sequence
  (BANK7@0x5D62: opcode 1, 48 data bits, opcode 2 time set, opcode 0 hold) ...
  NOTE: RTC counters set to 01:05:30 on day 02, month 1, year 00 - NOT RESTORABLE. To put
        the machine's clock back: TIME 01:05:30 and then DATE.
  set read-back: 0000110010100000100000000100000000001000000000001000
    payload at bit 0: sec=30 min=05 hour=01 day=02 mon/wday=10 year=00  (valid BCD)

    payload at bit 4: sec=53 min=10 hour=20 day=00 mon/wday=01 year=10  (valid BCD)
  fields matching the written pattern (bit0/bit4) = 06 00 of 6
  seconds-field alignment = payload at bit 0 (no prefix)  liveness: polling the seconds field for up to 2 s of ARTIC ticks ...
    -> the seconds field did NOT move: the calendar's counters are not running (a dead backup
       battery, or counters left held). Nothing on this machine can then be timed in absolute
       units. What would make it measurable: /TIMEREF /TIMESET, which writes a known time into
       the counters (and says so - it is not restorable), or a working battery.
  notes: the PIT line is the strong one - it uses no ARTIC rate and no CPU timing, only the
  PIT reload count, the divisor and the calendar's second. If the ARTIC line disagrees with the
  documented 307200 Hz, the ARTIC is not the clean timestamp source the tree's other reports
  assume, and the PIT-derived columns are the ones to quote. The CPU line is an effective rate,
  not a clock.
END:TIMEREF
